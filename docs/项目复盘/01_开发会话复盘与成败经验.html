2. 成功经验（可固化）

2.1 里程碑端测门禁

每个里程碑必须有指定环境的端到端证据，才能开下一阶段。

S0 的 S0_E2E_ENV + S0_PG_CLAIM_ONE_PASS 是原型；S1–S4 的开发机 PG 日志、预发四角色端测、S7 生产端测是同一纪律在不同阶段的展开。

2.2 积分与批次按张可对账

部分成功场景用「每张处置 + 批次合计」验收；明确禁止整批一口价叙事。对账可以用 fixture 换确定性，但不得把 fixture 样本写成「新的生产检测小样」。

2.3 先清单后编码、小步合入

DEV_INSTRUCTIONS 要求阶段具备 tasks / exit_evidence / forbidden 才开工；功能以 PR 合入 main，复盘与对外叙述只认已合入事实。生产后 UX 按 P0/P1/P2 轮次留验证记录，降低「改完无证」。

2.4 合同权威顺序

产品行为听 PRD，落地结构听架构，阶段路径听 DEV_INSTRUCTIONS；冲突停止实现并提问。

3. 失败教训与返工类型

教训 1：环境错位导致的「假完成」

  • - 表象：本机 pytest / Cloud CI 已绿，阶段却在开发机 PostgreSQL、claim_one、worker 消费等关键项上站不住；口头或进度文件容易先写成「S0 完成」。
  • - 根因：把「方便跑通的验证环境」默认为「主验收环境」。S0 的队列认领、租约与持久化行为依赖真实 PG，SQLite/Cloud 替身无法覆盖。
  • - 代价：若未拦住，会带着未证底座进入 S1，后续单张闭环与积分流水的失败更难归因。
  • - 证据：第 1 章；/tmp/s0-pg-claim-one-smoke.log → S0_PG_CLAIM_ONE_PASS；门禁名 S0_E2E_ENV；PR #19/#20。
  • - 固化：为不可替代项单独命名门禁与日志标记；未出现约定 PASS 字符串不得关项、不得开下一阶段。

教训 2：话术跑赢能力

  • - 表象：商家路径能出 JPG、生图能入库、调参试点分数有提升时，对内对外容易说成「检测已通过」「供应商已接通」「已可卖」「已默认晋升」。
  • - 根因：演示压力与阶段边界不同步；「能看见结果」与「合同意义上的通过/接通/收费」被揉成一句话。
  • - 代价：后续阶段被迫反复澄清；一旦对外使用错误承诺，撤回成本高于补证据。
  • - 证据：第 2/4/6 章；阶段清单区分 S1 替身 vs S3 真 Gemini；S5 证据含 supplier_connected=false；调参 PR 标题含 no default promote。
  • - 固化：对外句子必须能指回阶段清单与证据字段；固定四分法——替身 / 真模型调用 / 供应商接通 / 收费开放——禁止互相冒充。

教训 3：有台无实 / 不诚实占位

  • - 表象：S6 运营菜单、工单台、用户管理等页面齐全，但预审仍可能是占位、解冻/加减分等关键写路径不通，或文案让人以为「已经上真」。
  • - 根因：先铺信息架构与路由，后补真实供应商与写路径；验收若只点菜单打开，会漏掉「动作是否生效、口径是否诚实」。
  • - 代价：技术客服/管理员无法履职，或按错误口径操作；BLOCKING-FIX / PARTIAL-ALIGN / 浏览器端测被迫多轮返修。
  • - 证据：第 5 章；PR #27/#28/#32；/tmp/s6-pg-e2e.log → S6_PG_E2E_PASS。
  • - 固化：运营页验收以关键写路径（预审、解冻、加减分、预设启停等）真实可跑 + 诚实文案为准，不以「菜单在」为准。

教训 4：批次积分若按「整批感觉」验收必翻车

  • - 表象：1–10 张批次里部分成功、部分前置失败时，若只看「这批好像扣了分」，说不清每张是消费还是释放，也说不清合计是否等于假「整批一口价」。
  • - 根因：验收粒度停在批次或 API 总览，没有强制「每张处置分列 + 双张对照样本」。
  • - 代价：积分客诉无法用日志自证；fixture 对账样本还可能被误写成「新的生产 Gemini 小样」。
  • - 证据：第 3 章；/tmp/s4-pg-e2e.log → S4_PG_E2E_PASS（例：task40 消费 10、task41 释放 10，flat_batch_fee=false）。
  • - 固化：过关最低证明 = 开发机 PG 按张分列日志 + 至少一单「成功消费 / 失败释放」双张对照；fixture 与真检小样分栏陈述。

教训 5：生产依赖临期

  • - 表象：最终检测外呼依赖第三方订阅出口节点；节点名称自带到期日（约 2026-12-06）。到期未替换则检测链路中断，商家任务会卡在检测环节。
  • - 根因：为解除地域/出口阻断，临时落地第三方节点并完成了当时的端测；临期风险若不当成一等生产依赖登记，容易拖到临近到期才处理。
  • - 代价：检测从「业务可用」突然变为「基础设施不可用」；与「检测分数高低」无关，是通路问题。
  • - 证据：第 7 章；S7 收口残余 R7；REALPHOTOS-S7-PROD-DEPLOY-E2E-2026-11-16*。
  • - 固化：第三方/出口类依赖必须登记到期日与替换方案；替换先于到期执行，并在切换后抽检处理→检测主路径。

教训 6：显示回归被 API 断言放过

  • - 表象：接口返回里字段存在、状态码 200，自动化或抽检就判 PASS；但页面表格/顶栏/空态仍错——例如流水对不上任务号、列被挤掉、文案与扣费语义不一致。人眼或截图才能发现。
  • - 根因：把「数据层正确」当成「体验层正确」。API 断言不覆盖 CSS 布局、条件渲染、文案键绑定和空态分支。
  • - 代价：生产后 UX 被迫按 P0→P1→P2 多轮返修；客服对账与商家理解成本上升；若只合并「接口绿」的 PR，显示债会累积。
  • - 证据：第 8 章；UX 轮次 #70–#88 与 REALPHOTOS-UX-* 验收记录；流水任务号等专项（如 #71）；wiki 亦强调勿用 API 样本代替渲染表验收。
  • - 固化：体验相关改动以实际页面渲染（Playwright DOM / 截图 / 真人点表）为验收对象；每轮留下验证记录；关键对账页必须能从显示回溯到业务锚点（如任务号）。

4. 同类 AI 协同交付｜避坑清单（SOP 摘要）

  1. 1. 只认指定环境端测标记，本机/CI 绿不能自动关项。
  2. 2. 开下一阶段前，本阶段 exit_evidence + 端测必须齐。
  3. 4. 积分按张：部分成功要有分列证据。
  4. 5. 运营台先证写路径，再谈菜单完整。
  5. 6. 调参默认晋升必须显式门禁；试点默认不晋升。
  6. 7. 部署成功与收费开关解耦表述，避免用收费状态否定已完成的发布证据。
  7. 8. 生产第三方依赖登记到期日。
  8. 9. 体验验收看渲染，不只看 API。
  9. 10. 复盘数字以采集 JSON 为准，不用过期 handoff 口述改数。
  10. 11. 合入纪律抽象化：PR 进 main、禁止直接推保护分支、关键门禁必过（细节见仓库 AGENTS.md，本文不展开账号争议）。
  11. 12. 密钥与主机信息不进复盘正文。
