P0｜当前版本高优先级不足

P0-1 最终检测依赖临期第三方出口

  • - 现状：生产检测外呼经第三方订阅出口节点，节点名携带到期日约 2026-12-06；到期未替换则检测链路中断（S7 残余 R7）。
  • - 方案：替换为自有/长期可控出口；切换后抽检商家「处理→最终检测」主路径。
  • - 收益：检测能力不因临期节点停摆。
  • - 风险与工作量：中（采购/网络）；约 0.5～2 人周（不含采购周期）。

P0-2 资源 URL 导入未作为正式可用能力打开

  • - 现状：上线前清单中导入职责仍为停用；S7 亦记 R4（导入基址未完成对象级导入确认）。商家侧「URL 导入」不能当作已上线主路径宣传。
  • - 方案：确认正式供应商基址与样例对象 → 启用导入合同 → 用真实 URL 跑通入库并留产品验收。
  • - 收益：补齐批量获客/素材进入口。
  • - 风险与工作量：中（依赖供应商确认）；约 1～2 人周。

P0-3 验收/演示账号仍为种子口令

  • - 现状：生产仍使用种子口令账号（S7 R6）；面向真实客户或对外演示前存在冒用风险。
  • - 方案：上线前轮换为强口令；必要时区分内部验收号与对外演示号。
  • - 收益：降低账号被猜中/误用风险。
  • - 风险与工作量：低；0.5 人日级（含通知相关角色）。

P1｜当前版本可改进（非阻断）

P1-1 JSON 导入缺少必填提示

  • - 现状：已知非阻塞项——JSON 导入条目必须带 name，页面暂未提示，失败时商家不易理解。
  • - 方案：表单/上传校验前置提示「每条须含 name」；错误回显指向缺失字段。
  • - 收益：减少无效导入与客服解释。
  • - 风险与工作量：低；0.5～1 人周。

P1-2 单 worker 顺序处理导致大批次等待长

  • - 现状：已知非阻塞项——单 worker 顺序处理时，约 50 张量级可达约 70 分钟量级等待，商家体感「排队久」。
  • - 方案：在合同与架构允许范围内评估多 worker/并发上限，或产品侧展示更清晰的队列位置与预计等待。
  • - 收益：大批次可预期、少催单。
  • - 风险与工作量：中（并发与积分对账）；2～4 人周 起。

P1-3 检测/处理默认策略对运营不够直观

  • - 现状：生产可改检测模型合同，但业务侧仍不易一眼看清「当前默认策略版本、最近抽样概况、能否回退」。
  • - 方案：管理端展示当前最终检测/关键处理默认参数摘要与最近抽样概况；变更可回退。
  • - 收益：调参与客服话术一致，减少内部误解。
  • - 风险与工作量：中；1～3 人周。

P2｜规模化与商用前准备（当前能力边界）

P2-1 同机部署的容量与单点上限

  • - 现状：生产为应用与 PostgreSQL 同机（T01-B，R1 已接受单点）；业务量上升后可用性与磁盘/库压力会成为产品瓶颈。
  • - 方案：按架构升级路径准备库/盘/进程拆分选项；不把 OSS 必选写成当前必做。
  • - 收益：量上来时有明确扩容选项。
  • - 风险与工作量：高；单独立项。

结语

本文件只跟踪现行部署仍在的产品缺口：检测出口临期、导入未正式启用、口令商用化、导入提示与吞吐、策略可见性，以及单点容量与收费就绪。已修复的历史问题与已被更新证据否定的「通过率偏低」判断，均不列入。
