# 出云脱敏：把数据交给外部模型之前

> 回流说明（2026-08-27）：引擎实现位于 base `app/core/redaction/`（自 下游日报分支 的 `capabilities/daily_reports/redaction` 提升为内核工具，纯 Python、与方言无关）；测试 `tests/test_llm_redaction.py`。业务包只需 `from app.core.redaction import ...`，租户级策略存储仍属各业务包。

面向所有会把用户数据发给外部大模型的模块。本文写设计与边界，落地接口在
`docs/dev/guide_docs/`（模块接入时补），当前唯一实现在 `daily_reports` 能力包的
`redaction/` 子包，业务无关的部分按 `flows/NEW_MODULE.md` §0.1 的晋升标准
（被 ≥3 个互相独立的模块使用且协议稳定）再考虑上收到底座。

## 0. 一句话

**默认什么都不发；只发批准过的东西；发之前再查一遍，查出来就不发。**

## 1. 为什么要重写

这个能力最初的实现是一组正则：认出手机号、身份证、邮箱就替换掉。它在真实中文
语料上**几乎完全失效**，而且失效得毫无声响。

```
输入  客户手机13800138000，请回电
输出  客户手机13800138000，请回电        ← 一个字都没挡住
```

原因是 `\b`。Python 的 `\b` 是 `\w` 与 `\W` 之间的边界，而**中文字符在 Unicode
模式下就是 `\w`**——"机"和"1"两边都是 `\w`，边界不成立，整条规则静默跳过。中文
工作记录里手机号几乎总是紧挨着中文，于是这条规则在测试里绿着，在生产里全漏。

修掉 `\b` 只解决了这一个 bug，解决不了**方法**的问题：

- **denylist 天生漏。** 规则是"认出坏的"，而坏的写法是开放集合：全角数字
  `１３８００１３８０００`、分隔符 `138-0013-8000`、"尾号 8000"、
  拆成两句写、汉字数字。每补一条规则只是把已知的洞补上，未知的洞照旧。
- **漏了没有任何信号。** 数据已经出云了，没有异常、没有日志、没有告警。
  这类"静默降级"只能靠人工抽查发现，而抽查覆盖不了长尾。
- **抹掉之后模型也变笨。** `[客户]` 让模型分不清两个客户是不是同一个，
  指代关系断掉，产出的引用和归因质量一起下降。

方法上要换成：**尽量"知道"，而不是"猜"**；猜的部分只当兜底；最后再加一道
只做一件事的守卫。

## 2. 威胁模型

在防谁、不防谁，先说清楚，否则容易把力气用错地方。

| 对象 | 防不防 | 说明 |
|---|---|---|
| 外部模型服务商看到不该看的个人信息 | **防** | 这是本能力的唯一目标 |
| 请求日志、模型训练留存 | **防**（同上） | 出去了就假设会被留存 |
| 本租户内的越权查看 | 不防 | 那是 RBAC 与 DataScope 的事 |
| 用户自己故意把敏感信息塞进去 | **部分防** | 守卫拦截 + 明确告知，但不做内容审查 |
| 模型被提示注入后回吐原文 | 防 | 模型根本没拿到原文，只有假名 |
| 通过假名跨报告关联同一个人 | 防 | 假名编号**不跨记录复用** |

一个明确的**非目标**：这不是"匿名化"。按《个人信息保护法》第七十三条的区分，
去标识化后的数据**仍然是个人信息**（因为存在还原途径），匿名化才不是。我们做的
是去标识化 / 假名化（GDPR Art. 4(5) 的 pseudonymisation），所以**映射关系本身
必须当作敏感数据保护**——它只活在单次请求的内存里，不落库、不进日志。

## 3. 四层

按可靠性从高到低排，越靠前越应该承担主要工作量。

```
              ┌─ L1 字段策略（allowlist）────── 知道：这个字段是什么
输入 ─────────┼─ L2 已知值回扫 ──────────────── 知道：这个值是什么
              ├─ L3 模式探测（denylist）─────── 猜：这看起来像什么
              └─ L4 出站守卫（fail closed）──── 最后一眼：还有没有漏的
                                                     │
                                              命中 → 拒绝发送
```

### L1 字段策略：allowlist

结构化字段按策略处理，**未在策略里声明的字段一律不发**。这是 allowlist 的含义：
新增一个字段，如果没人去策略里给它定性，它默认出不去，而不是默认出得去。

五种动作，覆盖了 ISO/IEC 20889 里常用的几类去标识化手法：

| 动作 | 手法 | 用在哪 | 例 |
|---|---|---|---|
| `pass` | — | 确认不含个人信息且模型需要 | 工作内容描述 |
| `pseudonymize` | 假名化 | 需要保留指代关系的实体 | 客户名、联系人、成员名 |
| `generalize` | 泛化 | 量级有意义、精确值不必要 | 金额 → `10万-50万` |
| `hash` | 令牌化 | 只需判断是否相同，不需要还原 | 设备号、外部账号 ID |

`hash` **不能用在身份证、银行卡上**。它们取值空间可枚举，无盐哈希还跨记录稳定
可关联——那不是阻断，是换了个形式的标识符。这两类无论策略怎么配都走 `block`。
| `block` | 抑制 | 任何情况下都不该出云 | 身份证、银行卡、密码 |

`block` 的字段如果同时出现在自由文本里，L2 会把它替换掉；替换不掉则由 L4 拒绝。

### L2 已知值回扫：这一层是重点

用户填在结构化字段里的**真实值**，同一份记录的自由文本里往往还会再出现一遍。
既然我们已经知道"张伟"是联系人、"13800138000"是他的手机，就不需要再去正文里
猜——直接按值替换。

这是"知道"与"猜"的分界，也是整个设计里性价比最高的一层。

匹配必须做**变体展开**，否则等于没做：

| 类型 | 展开出的变体 |
|---|---|
| 手机 `13800138000` | 全角形式、`138-0013-8000`、`138 0013 8000`、`138-00138000`、以及在"尾号/末四位/后四位"之后出现的 `8000` |
| 姓名 `张伟` | 本名；开启别名派生时另加 `张总` `张经理` `张先生` `张女士` `小张` `老张` |
| 机构 `华为技术有限公司` | 本名；剥离 `有限公司/股份有限公司/集团/公司` 等后缀得到 `华为技术`；再取长度 ≥2 的前缀 `华为` |

两条实现纪律：

1. **长值优先。** 先替换 `华为技术有限公司`，再替换 `华为`，否则前者会被后者
   切成 `〔客户1〕技术有限公司`。
2. **替换过的区间要遮住。** 否则第二轮规则会在假名内部再匹配一次。

别名派生（`张总`）会带来过度匹配的可能，但在一份工作记录的语境里，`张总` 几乎
必然就是那个张伟。**过度脱敏的代价远小于漏脱敏**，所以默认开启，并留开关。

### L3 模式探测：只当兜底

L1/L2 覆盖不到的（用户手打了一个没登记的号码），靠模式识别。规则本身要处理
中文语境：

- 不用 `\b`，用显式的"前后不是数字/字母"环视
- 匹配前先做 NFKC 规范化，把全角数字折成半角
- 身份证排在手机号前面（18 位不能被 11 位规则切一段走）
- 银行卡排在通用长数字前面

这一层的定位是**降低 L4 拒绝率**，不是主力。任何时候发现"要靠加正则来保证安全"，
说明 L1/L2 没做到位。

### L4 出站守卫：唯一真正的保证

在 payload 交给 HTTP 客户端之前，用一组**独立的**高危规则再扫一遍。

它必须满足三个条件，否则就是自欺欺人：

1. **独立实现。** 不复用 L3 的规则对象、不共享它的假设。纵深防御的最后一层
   如果和前面共用同一个错误前提（比如都用 `\b`），那它一起失效。
2. **只判有无，不做修补。** 职责越小越不容易错。
3. **fail closed。** 命中就抛异常、不发送。默认策略是 `reject` 而不是
   `redact` ——"尽力清理后照发"在合规上等于没有承诺。

被守卫拦下时**不回显原值**，只告诉用户"第 X 段疑似包含手机号"。

## 4. 假名化，而不是抹除

`[客户]` 与 `〔客户1〕` 的差别不是审美：

```
抹除   拜访了[客户]和[客户]，[客户]签了单
假名   拜访了〔客户1〕和〔客户2〕，〔客户1〕签了单
```

抹除之后模型无法判断"签单的是前面哪一家"，指代关系整个塌掉，它给出的归因和
证据引用会跟着变差——**为了隐私把产品做坏了，最后两头不讨好**。

### 假名格式

`〔类型序号·nonce〕`，例如 `〔客户1·a7f3〕`。
用 U+3014/U+3015 全角龟壳括号：中文商务文本里几乎不出现，视觉上一眼可辨，
模型也不会把它当成需要"修正"的错别字。

序号**每条记录从 1 开始**，不跨记录复用。跨记录复用会让"客户 7"在多份报告间
可关联，等于自己削弱了去标识化强度。

末尾那段随机 nonce **不是装饰，是正确性的必要条件**。没有它的时候：

```
用户写的     备注〔客户1〕是内部编号，另外拜访了华为技术
还原之后     备注华为技术是内部编号，另外拜访了华为技术
                ^^^^^^^^ 用户没写过这四个字
```

用户自己在正文里写一句形似假名的内容，就会和生成的假名撞上，还原时把他的原文
改掉——**数据损坏，而且悄无声息**：他要翻历史才会发现，那时已经说不清是谁改的。
同一个洞也会让容错还原把 `【客户1】的报价单` 一起改掉。

nonce 每次请求重新生成，用户写不出来，"生成的假名"与"用户碰巧写的相似文本"
从此可区分。代价是假名难看了一点，而模型并不在意。

### 还原（re-identification）

模型返回的结果里会带着假名——摘要、评分依据、原文引用都是。**返回路径上必须
还原**，否则人看到的证据引用和他眼里的原文对不上，整个"可解释"的承诺就废了。

```
模型看到   〔客户1〕本月回款〔金额1〕
人看到     华为技术本月回款 18 万
```

还原要对模型的排版改动有容错：模型可能把 `〔客户1·a7f3〕` 写成 `[客户1·a7f3]` 或
`【客户 1·a7f3】`。匹配时括号和空格都当可选，**但 nonce 必须对上**——
容错的是括号写法，不是身份。

映射表本身随请求生命周期存活，**不落库、不进日志**。

但要把话说准，否则文档会变成一句好听的空话：**还原之后的结果是落库的**。
模型返回的摘要和证据引用还原后写进调用留痕，组长审核时看的就是它——
不落库的话，他打开审核页只能看到 `〔客户1〕`，"证据可回溯到原文"的承诺就没了。

所以边界是这样划的，三样东西三种待遇：

| 内容 | 落在哪 | 敏感度 |
|---|---|---|
| 出云请求快照 | 调用留痕的 `request_payload` | 已脱敏，可按技术日志留存 |
| 还原后的模型产出 | 调用留痕的 `result_payload` | **与日报正文同级**，留存策略必须一致 |
| 命中摘要（几处手机号） | 审计事件 | 无原值 |

**审计事件里一个业务内容都不许有。** 审计是只追加、长期保留的，把内容塞进去
等于凭空多出一份需要同等强度保护的副本，而且删不掉。要看内容去看日报本身。

## 5. 策略是一份需要签字的东西

"未经批准的字段不得发送"里的**批准**必须有载体，否则这句话没有执行力。

策略表按租户、**只追加**：

```
tenant_id | version | rules(JSON) | approved_by | approved_at | note | is_active
```

- 改策略 = 新增一个版本并置为 active，旧版本留着
- 每次模型调用把 `policy_version` 记进调用留痕
- 于是任何一次历史调用都能回答"当时按哪套规则脱的敏、谁批的"

没有这张表，合规问答就只能靠口头记忆。

## 6. 交互：透明比阻止更重要

这一节是产品判断，不是合规要求。

用户会不会信任这套东西，取决于他**能不能看见它在做什么**。看不见的保护等于
没有保护——用户要么以为没脱敏而不敢写，要么以为脱敏了而乱写。

三条：

1. **写的时候就提示，但不拦。** 字段失焦即本地扫描，命中就在下方标一行
   "这里像是手机号，AI 不会看到它"。不弹窗、不禁用提交。让人知道，不替人做决定。
2. **给出"AI 看到的版本"。** 一个可展开的预览，逐字显示实际发出去的内容。
   这是整套设计里最便宜也最有效的信任装置。
3. **被拒绝时不能是死路。** 守卫拦截后必须同时给出"不使用 AI，直接提交"的出口。
   隐私保护不该变成完不成工作的理由，否则用户会绕过它。

审核/查看侧：证据引用显示**还原后的真实值**，旁边标一句"AI 看到的是假名"。

### 点选确认，而不是填表

要让 L2 生效，需要知道哪些值是实体。最直接的办法是让用户填结构化表单
（客户名、联系人、手机各一栏），但这与"减少填写负担"的产品目标正面冲突，
在手机上尤其如此。

采用的做法是**候选 + 一次点选**：服务端本地（**不调用任何模型**）识别出可疑片段，
在正文里列出来，用户点一下选"客户名 / 联系人 / 都不是"。

- 没识别到东西时，用户零额外操作——这是常态，必须做到真的安静
- 识别到时，一次点击就把"猜"升级成"知道"，L2 从此按真值精确替换
- 用户不点也不影响：该假名化的照样假名化，只是精度低一些

识别绝不能调用外部模型——"为了脱敏先把原文发出去"逻辑上自相矛盾。

中文识别的两个实际问题：

- **机构名**靠后缀锚定（`XX有限公司`/`XX科技`）。正则往左是贪心的，会框成
  "上午拜访华为技术有限公司"，得把时间词、动词和虚词从左边裁掉。框得准不准
  只影响体验、不影响安全——但框得离谱会让用户不信任它，进而不用它，
  那安全性就真的受影响了。
- **人名**不猜，只认称谓形式（`张总`/`李经理`）。中文姓名没有词边界，
  又常与普通词同形，直接猜会大量误伤。

确认结果存在记录上，成为下一次调用的已知值。审计只记"确认了几个、什么类别"，
**不记值**——值本身就是要保护的东西。

## 7. 怎么验证它真的有效

安全能力最容易出现的问题是"测试全绿但一个都挡不住"——本能力的第一版就是。

**红队语料**是硬要求：一份样本文件，每条给出输入和"**绝不允许出现在输出里的
字符串**"，CI 里逐条断言。至少覆盖：

- 中文紧邻（`客户手机13800138000`）——第一版就死在这里
- 全角数字、分隔符变体、"尾号 8000"
- 姓名与常见词同形
- 跨字段拼接：结构化字段里的值出现在自由文本里
- 长值/短值嵌套（`华为技术有限公司` 与 `华为`）
- 守卫必须拒绝的场景

另一条纪律来自 `flows/NEW_MODULE.md` §8：**每个新增的扫描器都要注入一次真实
违规并确认变红**，还原后变绿。没做过这一步的安全测试，不能算数。

## 8. 落地边界

- 引擎是纯函数：输入文本与策略，输出结果与映射，不碰数据库、不发网络请求。
  这样才能被红队语料直接驱动。
- 模型调用**永远在数据库事务之外**（轻量 SQLite 部署下写事务是全库串行的）。
- 引擎内核不出现任何业务词汇，为将来上收到底座留路。
- 留存：调用留痕的**请求**快照是脱敏后的，原文不进这张表、也不进任何外部请求日志；
  但**响应**是还原后的，敏感度与日报正文同级，留存策略要一起定。

## 9. 已知取舍

- **过度脱敏优先。** 别名派生、机构名前缀匹配都会误伤无关文本。在工作记录
  语境里这个代价可以接受，反过来不行。
- **泛化会削弱证据。** 金额泛化成区间后，模型给不出"回款 18 万"这种精确依据。
  默认泛化、可由租户在签字后改成 `pass`，把决定权交给有权决定的人。
- **守卫会误拒。** 长订单号、纯数字的产品型号都可能触发。所以必须有"不用 AI
  直接提交"的出口，并把误拒当作策略调优的输入。
- **本地识别不如模型准。** 但识别本身绝不能调用外部模型——那就成了"为了脱敏
  先把原文发出去"。
- **假名带 nonce 之后，模型若删掉 nonce 就还原不了。** 实践中模型会原样复制
  括号里的内容，但这是个真实的失败模式：宁可显示成代号，也不能为了容错而放宽到
  "看见 `〔客户1〕` 就还原"——那正是会改掉用户原文的那条路。

## 10. 租户级策略：分级 + scope（2026-08-28 落地）

- **存哪**：`tenant_redaction_policies`（`app/domain/ai_redaction`），按 `(tenant_id, scope)` 版本化只追加；通用 scope `*` 管实体类别 / 白名单 / 守卫姿态，模块 scope（如 `daily_reports`）管字段级放行。`load_policy(db, tenant_id, scope, default)`：模块 scope → `*`（叠模块默认 fieldRules）→ 模块默认。
- **分级**：`level = off | basic | standard | strict | custom`。basic 只抓强标识（手机/证件/卡号/邮箱）、不派生、金额不泛化、守卫 warn；standard 加人名/机构/地址与派生、守卫 reject；strict 再加金额泛化、白名单清空；custom 从某个 `baseLevel` 出发按高级 JSON 覆盖。`off` 只能在通用 scope 显式签字设置，审计记录 version + level。
- **入口**：租户设置 → AI 页签"AI 出站脱敏"卡片（租户管理员）；API `GET/PUT /tenant/profile/settings/ai-redaction`、`GET …/versions`。模块自己的设置页只保留"本模块是否启用 AI / 是否强制脱敏"开关。
